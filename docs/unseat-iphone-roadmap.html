Executive summary

Recommendation and why
Recommendation Build a Home Screen web app (PWA). Unseat serves it itself, on 127.0.0.1 only, and Tailscale Serve publishes it privately to your own devices over HTTPS. Unseat sends reminders through Apple Web Push straight from Windows, with no Unseat cloud server and no third-party push service.

Why this approach

  • Fact iPhone web apps get push notifications on iOS 16.4 and later. They must be added to the Home Screen, and the user must allow notifications by tapping a button. No Apple Developer account is needed. (Apple developer docs, WebKit blog)
  • Fact A native app installed without the App Store needs a Mac with Xcode to build it. With a free Apple ID it stops working after 7 days and cannot get push notifications. Push needs the $99/year Developer Program. (Apple membership comparison)
  • Fact A plain web page (no Home Screen install, no push) can't alert you while it's closed or in the background, so on its own it doesn't meet the "same reminders" goal.
  • Fact Push and the service worker need a real HTTPS address with a trusted certificate. Tailscale Serve gives the PC one (<machine>.<tailnet>.ts.net, a Let's Encrypt certificate) that only your tailnet can reach. (Tailscale docs)
  • Recommendation The PWA can be plain HTML/JS built into unseat.exe: no npm, no framework, no separate hosting. That keeps maintenance low and matches how Unseat already ships as one file.

What it needs from outside your PC

  • Apple Push service (*.push.apple.com) carries each reminder. The message is encrypted end to end. Apple still sees when it was sent and which device it went to.
  • Tailscale (free Personal plan) on the PC and the iPhone, for the private HTTPS address and for remote access.
  • Let's Encrypt issues the certificate. Your PC's Tailscale machine name appears in public Certificate Transparency logs.

Main limits to accept

  • The phone gets reminders only while the PC is awake, running Unseat and online. The timer runs on the PC.
  • Apple publishes no delivery-time guarantee for web push. Real-world delay has to be measured on your phone (Phase 1).
  • Same-Wi-Fi use without Tailscale is not recommended: a LAN IP address can't get a publicly trusted certificate. See decision D3.
  • Turning this on adds a network listener (loopback only, off by default) to an app whose SECURITY.md and ARCHITECTURE.md currently say "no network". Both docs need updating when it ships.

Fit with the current code

  • Fact Unseat is a single-threaded Win32 app. App owns the engine and runs everything from the hidden window's messages (src/win/app.rs:762). The new server must run on its own thread and hand each request to the UI thread as a window message. It must never touch App directly.
  • Fact All remote controls already exist as Command::{TogglePause, Reset, Snooze, StartBreak} (src/engine.rs:39), run by App::apply_engine_command (src/win/app.rs:300). Remote settings can reuse App::apply_settings (src/win/app.rs:490), which already keeps live state and clamps values.
  • Fact Reminder text comes from alert_actions() → Notice (src/alerts.rs:29). Only time-up and break-over produce a notification; repeat reminders play a sound only. The phone push should hook in next to tray::notify in App::handle_beep (src/win/app.rs:247).
  • Recommendation Following ARCHITECTURE.md ("the host must not invent timer rules"), put protocol, pairing, push encryption and sync rules in the Win32-free library so they're unit-tested on any OS. Only sockets, WinHTTP and DPAPI go in src/win/.

Design details

Pairing · auth · notifications · controls · offline · battery · privacy

1. Secure pairing (QR)

  1. In Settings → Phone, the user turns the companion on. Unseat checks that Tailscale Serve is set up and shows the https://…ts.net address.
  2. "Pair iPhone" makes a one-time code: 128-bit random, valid 5 minutes, single use, 5 tries at most. Unseat shows a QR of https://<host>.ts.net/#pair=<code> plus a short code to type by hand. The # part never reaches server logs.
  3. The phone opens the link in Safari. Fact Home Screen web apps have separate storage from Safari, so the page first walks the user through Add to Home Screen. Pairing then finishes inside the installed app, where the user types the short code.
  4. The PC asks for local confirmation ("Allow 'iPhone'?") before the device gets a credential.
  5. The phone gets a device ID plus a 256-bit secret. The PC stores only a SHA-256 hash of it.

2. Authentication & access

  • Network layer: only devices on your tailnet can reach the address (Tailscale Serve, not Funnel).
  • App layer: every API call carries the device credential, compared in constant time. Origin is checked; no CORS.
  • Extra check: Tailscale Serve adds a Tailscale-User-Login header and strips any copy a client sends. Unseat can require it to match the login saved at pairing. Fact header behaviour per Tailscale docs.
  • Revoking a device deletes its hash and push subscription and closes its open streams at once.

3. Notification sync

  • Trigger (D4, approved): every Unseat reminder is mirrored by default: time-up, break-over and repeat reminders, sent from handle_beep. Repeat reminders only play a sound on Windows today, so they need new push text. Optional setting: idle-only (push only while the PC is idle or locked).
  • Payload: declarative Web Push JSON ("web_push": 8030, title, body, navigate), plus a service worker that shows the notification for iOS 16.4–18.3. Encrypted per RFC 8291; signed with VAPID.
  • Headers: Urgency: high, short TTL (a stale "stand up" is useless), and Topic so a newer alert replaces an undelivered one.
  • Fact Safari cancels the subscription if a push isn't shown, so any "don't alert" choice is made on the PC (don't send). The phone never silently drops a push.
  • On 410 the subscription is removed and the device is marked "notifications off — reopen app".

4. Remote controls & two-way settings

  • Controls: pause/resume, reset, snooze (preset), start/end break. Each maps 1:1 to an existing Command.
  • Settings: a whitelisted subset (sitting limit, break length, repeat reminders and interval, sound, volume, notifications, snooze length). Machine-specific settings (autostart, hotkeys, window position, dock) stay PC-only. Final list is decision D6.
  • Sync: the PC is the source of truth and keeps a revision number. A change sends If-Match: rev; a stale revision gets 409 plus the current values. Changes made on the PC reach the open app over a live event stream.
  • The Windows settings window gets the same rule, so it never overwrites a newer phone change without warning.

5. Offline & reconnection

  • The service worker caches the app shell, so the app opens with no connection and shows the last state with "last updated …".
  • Reconnect on visibilitychange / online, with backoff (1 s → 30 s, with jitter). No background polling. Fact iOS has no Background Sync or Periodic Sync for web apps.
  • Controls are disabled while offline. Nothing queues, because a delayed "pause" would be wrong.
  • PC asleep or Unseat closed: no pushes. The app shows "PC not reachable".
  • Phone offline: Apple holds the push up to its TTL, then drops it.
  • PC can't reach Apple: retry with backoff, give up when the TTL ends, and log it.

6. Delays, battery & privacy

  • Delay: Apple publishes no delivery bound. Unknown until measured on your phone. Focus modes can hold notifications back. Fact (WebKit)
  • Phone battery: the PWA does nothing in the background except show pushes (about one per sitting period). Tailscale's always-on VPN cost is Unknown; VPN On Demand rules can limit when it runs.
  • PC: one listener thread blocked on accept, no timers. Nothing at all when the feature is off.
  • Privacy: notification text is encrypted end to end. Apple sees timing and endpoint metadata. Tailscale sees device metadata. Let's Encrypt CT logs publish the machine name, so rename the PC first if its name is personal. No analytics, no third-party scripts.

What Phase 1 changed in the design

  • Observed On iOS 18.7, declarative pushes were shown but the service worker never reported them, while plain-JSON pushes did (3/3). Assumption The service worker only gets declarative pushes when the message opts in (a "mutable" flag); not confirmed in Apple's docs.
  • Decision for Phase 2 Unseat sends declarative messages (shown by iOS itself, so there is no service-worker revocation risk). Delivery tracking uses Apple's response codes, not phone receipts.
  • Observed The phone's clock was about 41 s ahead of the PC's. Expiry and duplicate rules use only the PC clock plus Apple's TTL.

Measurement: "PC clock" delay is push sent → the phone's service worker reporting back over the tailnet. It's an upper bound on delivery time. A receipt shows the service worker ran; your seen / not-seen marks are the evidence the notification was shown. Results land in spikes/iphone-push/data/results.json (gitignored) and get copied here after the run.

Security requirements

The Windows control API is never public
  1. Never public. The server binds 127.0.0.1 only and is reached only through Tailscale Serve. Funnel is never used, and setup docs say how to check it's off.
  2. Off by default. No socket, thread or outbound request until the user turns the companion on. Existing settings files load with it off.
  3. Pairing: one-time 128-bit code, 5-minute expiry, single use, 5 tries, local confirmation on the PC.
  4. Credentials: 256-bit random device secret; the PC stores only its SHA-256 hash and compares in constant time; secrets never appear in logs or settings.json.
  5. Every request authenticated. Origin checked; no CORS; changes require a custom header and a credential (prevents cross-site requests).
  6. Tailnet identity check: Tailscale-User-Login must match the owner saved at pairing (decision D2).
  7. Input limits: whitelisted commands and settings only, values clamped with existing Settings::clamp, 8 KB request limit, header timeout, connection cap.
  8. VAPID private key encrypted with Windows DPAPI (current user), stored apart from settings.json.
  9. Push content: only the alert title and body; no personal data; encrypted per RFC 8291.
  10. Revocation takes effect at once and also deletes the push subscription.
  11. PWA: strict Content-Security-Policy (default-src 'self'), no third-party scripts, no analytics.
  12. Local audit log of pair, revoke, and settings/command changes, with no secrets.
  13. Docs: update SECURITY.md, ARCHITECTURE.md and docs/windows-distribution.md (which currently say "no network") in the same change that adds networking.
